## Three things that should change how these numbers get used

### 1. ESTIMATE's purity formula is Affymetrix-only, and we are on Illumina

`estimateScore.R` computes `TumorPurity` **only** when
`platform == "affymetrix"`. For agilent and illumina it emits the three scores
and stops. The conversion

```
purity = cos(0.6049872018 + 0.0001467884 × ESTIMATEScore)
```

was fit on Affymetrix arrays against ABSOLUTE and the authors declined to
extend it. TCGA STAR counts are Illumina RNA-seq. Applying it anyway is common
in the literature and is an extrapolation off its calibration platform. That is
why the column is called `estimate_affy_extrapolated` and never plain "purity".

**How wrong is it? Look at the normals.** ESTIMATE gives normal-adjacent tissue
a median "tumour purity" of **0.692**. Normal colon is not 69% tumour. The
*ranking* is informative — it tracks Aran's own ESTIMATE at r = 0.994 — but the
absolute values are not on a meaningful scale. Use it as a relative covariate,
never as a percentage anyone quotes.

### 2. ESTIMATE is partly circular with our outcome; ABSOLUTE is not

ESTIMATE infers purity *from expression*, via stromal and immune signature
enrichment. Our outcome — GUCA2A, CDX2 — is also expression. Conditioning on an
expression-derived covariate removes some of the signal along with the
confounder, and the direction is not knowable in advance.

ABSOLUTE is called from copy-number and SNP data. It is the more independent
estimate and **should be the primary purity covariate**, with ESTIMATE as the
sensitivity analysis on the 18% of samples ABSOLUTE does not cover. The
`expression_derived` boolean is in the table so a model can be built either way
without anyone having to remember this paragraph.

### 3. The offset is systematic, not noise

ABSOLUTE sits a median 0.128 below extrapolated ESTIMATE, with the IQR entirely
negative (−0.227 to −0.055). Substituting one for the other does not add scatter,
it shifts the whole covariate. In a Cox model that is a changed coefficient, not
a wider interval.

## Provenance: this is a reimplementation, and here is why you can trust it

R does not run in this environment — `R.exe` exits 53 with no output — so
`estimate_scores()` is a direct port of `estimateScore.R` v1.0.13 into Python.
A reimplementation that quietly differs from the canonical tool is worse than no
tool, so it is validated two ways:

1. **Against the package's own reference output.** ESTIMATE ships
   `sample_input.gct` with the `sample_estimate.gct` it produces.
   `test_reproduces_the_packages_own_reference_output` asserts we match all
   three score rows to **rtol 1e-6**. It passes.
2. **Against real TCGA data.** Aran's table carries their own ESTIMATE purity.
   On the 379 overlapping samples, ours correlates at **r = 0.9937** (median
   absolute difference 0.071 — expected, since they scored a different
   expression build).

Two implementation details are load-bearing and neither is obvious from the
paper:

- **Scores are defined on the common-gene-filtered matrix**, not the raw one.
  `estimateScore` divides ranks by the gene count, so scoring 60,616 genes
  instead of ~10,000 shifts every score. We match ESTIMATE's `filterCommonGenes`
  first: **9,911 of 10,412 common genes matched (95.2%)**.
- **R's `merge` sorts by the join column**, and row order changes tie-breaking
  inside `order()`. The matrix is sorted alphabetically to match.

### A defect found in the package itself

`sample_purity.gct` **does not match the code that ships beside it.** Both
fixtures carry an identical ESTIMATE score row, so purity should be a
deterministic function of a number we reproduce exactly — it is not. Inverting
the fixture gives intercept 0.6036365441 / slope 0.0001506451, against the
source's 0.6049872018 / 0.0001467884, with a linear-fit residual of 8e-16.
The shipped example was generated by an earlier version of the conversion and
never regenerated.

**We follow the source, not the stale example.** The disagreement is at most
0.015 purity units. `test_the_shipped_purity_example_is_stale_relative_to_the_source`
pins this rather than hiding it behind a loose tolerance, so a future ESTIMATE
release that regenerates the example fails the test and makes someone re-read
the constants.

## Inputs

Both are external data: downloaded to `data/raw/`, recorded in
`data/manifest.csv`, **not committed**. The ESTIMATE package is GPL-2 and
vendoring its data raises a licensing question for no benefit; the Aran table is
a publisher's supplementary file.

| Input | Source |
|---|---|
| ESTIMATE 1.0.13 | R-Forge source tarball — signatures, common genes, reference fixture |
| Aran et al. 2015 Supplementary Data 1 | doi:10.1038/ncomms9971 — ESTIMATE / ABSOLUTE / LUMP / IHC / CPE |

`python -m src.bulk.run_purity fetch && python -m src.bulk.run_purity run`

**Join key is the 16-character sample barcode** (`TCGA-A6-2670-01A`). ABSOLUTE
is called from a DNA aliquot and our expression is RNA, so the full aliquot
barcodes never match; the sample is the finest level on which they agree.

## What this unblocks, and what it does not

**Unblocks the W3.2 re-run.** The premise check said bulk GUCA2A loss is
continuous, marked provisional pending purity. That re-run can now happen, and
should use `absolute` as the primary covariate.

**W3.6 covariate lock.** Purity is on the pre-specified list. The lock should
name *which* purity — recommendation: ABSOLUTE primary, ESTIMATE sensitivity,
never a coalesced column.

**Does not resolve** the 18% of samples with no ABSOLUTE call. A complete-case
model on ABSOLUTE drops 119 samples; an ESTIMATE-filled model changes covariate
meaning mid-column. That is a real modelling decision for W3.6 and it is not
made here.
